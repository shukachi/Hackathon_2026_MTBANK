# План: «Детско-семейный банкинг в Moby» — материалы хакатона + рабочий веб-прототип

## Контекст

МТБанк (Беларусь) проводит хакатон «Детско-семейный банкинг в Moby» (см. `TZ/Family banking_Hackaton.pdf` и `TZ/ТЗ_Хакатон_Дестко_семейный_банкинг.docx`). Официальное ТЗ требует 3 обязательных артефакта — Pitch Deck, Product Canvas, экономическое обоснование — но дополнительно нужен работающий демо-прототип («вебка»), не просто слайды. Проект стартует с нуля (только папка `TZ/` с исходными материалами), разрабатывается одним full-stack+AI разработчиком без жёсткого дедлайна.

Принятые решения на развилках:
- **Приоритет:** материалы и прототип — два параллельных равнозначных трека, ни один не второстепенный.
- **Стек прототипа:** React (Vite) фронтенд + Python FastAPI backend (mock банковское ядро) + локальная LLM через **Ollama** для AI-ассистента. Без мобильного React Native, без on-device llama.cpp/MediaPipe, без LoRA-дообучения — идея «локальный AI» реализована как «AI работает локально на машине через Ollama» — даёт тот же месседж «приватность + офлайн», но реализуется кратно быстрее одним разработчиком.
- **Авторизация и БД — обязательны**: никакого «переключателя роли без логина» — нужна настоящая регистрация/вход (родитель регистрируется, создаёт профили детей, входит по логину+паролю) и персистентная база данных, в которой реально хранятся пользователи, семьи, карты, транзакции и т.д.
- **Юридический раздел:** только общие общеизвестные принципы (ограниченная дееспособность несовершеннолетних, согласие законного представителя, защита персональных данных детей) без точных номеров статей ГК/Банковского кодекса/закона о персональных данных РБ (нет доступа к веб-поиску для проверки) — с явными пометками «⚠ проверить с юристом банка».

Цель — довести проект до защиты на хакатоне: честные, подкреплённые прототипом материалы + работающее демо, которое можно запустить одной командой на ноутбуке.

## 0. Сквозное концептуальное ядро

Единая формулировка продукта для всех артефактов: **«Moby Family»** — пакет внутри Moby, который родитель выпускает под возраст ребёнка (7–13 / 14–17 лет). Ребёнок получает физическую карту + персональный вход в Moby с правами, которые задаёт и в любой момент меняет родитель. Геймификация (квесты, награды, цели накопления) обучает финграмотности. Родитель — «последнее слово».

Возрастная дифференциация прав (сквозная таблица, нужна в материалах и как константа в коде):

| | Дети 7–13 | Подростки 14–17 |
|---|---|---|
| Карта | Физическая, детский дизайн | Физ + цифровая, онлайн-покупки |
| Операции | По умолчанию с подтверждением родителя | Самостоятельные в рамках лимита + запрос расширения прав |
| Функции | Карманные деньги, цель накопления, квесты | + подписки, партнёрские скидки, заявка на накопительный продукт |
| Юр. статус (⚠ проверить с юристом) | Сделки через/с согласия законного представителя | Может самостоятельно совершать мелкие бытовые сделки/распоряжаться своим заработком в установленных пределах |

Эта дифференциация — основной аргумент против «это просто детская карта + родительский контроль» (запрещённый ТЗ плагиат очевидной механики).

## 1. Материалы хакатона (`docs/`)

### 1.1 Pitch Deck (`docs/pitch-deck.md`, 10–12 слайдов)
1. Титул — «Moby Family» + тезис «Банк растёт вместе с семьёй».
2. Проблема (из презентации банка, слайд 2: родителям — контроль, детям — самостоятельность).
3. Решение в одной картинке: родитель выпускает пакет → ребёнок получает карту + вход в Moby с правами → геймификация.
4. ЦА — 3 персоны (родитель, ребёнок 7–13, подросток 14–17) из слайда 3 презентации банка.
5. Конкуренты/рынок — таблица по осям: геймификация, гибкость лимитов, интеграция в основное приложение семьи, возрастная дифференциация прав. Вывод-дифференциатор: всё внутри Moby + динамические права по возрасту + ребёнок сам запрашивает расширение прав.

7. Путь ребёнка — 4 шага из ТЗ, со скриншотами прототипа.

9. AI-ассистент как дифференциатор — работает локально (приватность данных детей, офлайн), чат для ребёнка + команды родителя на естественном языке.
10. Экономика (саммари таблицы из 1.3).
11. Win-Win (банк слева / семья справа, по слайду 11 презентации банка).

### 1.2 Product Canvas (`docs/product-canvas.md`)
- Problem / Jobs-to-be-done по каждому сегменту.
- Target Segments (с явно помеченными оценочными цифрами, если нет данных рынка РБ).
- Value Proposition по сегментам.
- **Схема потока** (ядро раздела, то что ТЗ называет «логика решения»):
  Родитель → оформление пакета (возраст + согласия) → core banking создаёт Family-профиль + карту ребёнка → ребёнок в ограниченном режиме → операция → проверка лимита/категории → push родителю при необходимости подтверждения → родитель подтверждает/меняет лимиты (замкнутый цикл).
  Отдельная ветка: ребёнок → запрос доступа к функции → уведомление родителю → approve/deny → право применяется.

- Control & Safety layer (лимиты, запрет категорий 18+/азарт, подтверждение операций, блокировка карты).
- Revenue streams / Cost structure — ссылка на 1.3.
- Key metrics (активные Family-профили, оборот по детским картам, % выполненных квестов, retention родителей, конверсия «ребёнок → взрослый клиент»).

Можно отрисовать flow-диаграмму как SVG/PNG — отдельная необязательная задача, не блокирует написание содержания.

### 1.3 Экономическое обоснование (`docs/economics.md`)
Явно отвечает на требование ТЗ (слайд 12 презентации банка): стоимость привлечения семьи, расходы на бонусы/мес, доход банка/мес, срок окупаемости.

- **Допущения** (явно пометить «модельные допущения для демонстрации логики расчёта»): средний оборот/остаток по карте ребёнка и подростка раздельно, % семей с доп.продуктом, CAC на семью, % кешбэка от оборота, затраты на разработку/поддержку.
- **Доходы банка/мес на семью:** оборот по картам (interchange), доход от остатков, партнёрские выплаты, маржа доп.продуктов.
- **Расходы банка/мес на семью:** амортизация CAC, бонусы/кешбэк, минимальные операционные расходы (фича внутри существующего Moby).
- **Итоговая таблица** (формат слайда 12 банка): CAC (BYN) / расходы на бонусы (BYN/мес) / доход банка (BYN/мес) / срок окупаемости (мес) = CAC / (доход − расходы).
- Абзац чувствительности («при росте оборота на X% окупаемость сокращается до Y мес»).
- LTV-аргумент — будущий взрослый клиент (нефинансовый, но упомянутый плюс).
- Явная пометка: «⚠ Допущения для демо-расчёта, требуют валидации реальными данными банка перед защитой».

### 1.4 Юридический раздел (`docs/legal-notes.md`)
Только общие принципы + явные пометки на проверку:
1. Ограниченная дееспособность несовершеннолетних: малолетние действуют через/с согласия законного представителя; подростки постарше (ориентировочно с 14 лет) могут самостоятельно совершать отдельные мелкие бытовые сделки и распоряжаться собственным заработком в установленных пределах. ⚠ Точные возрастные границы и применимость к банковским продуктам — проверить с юристом банка.
2. Согласие законного представителя фиксируется явным шагом в приложении (чекбокс + отметка даты/времени). ⚠ Требования к форме/доказательной силе электронного согласия — уточнить у комплаенс банка.
3. Персональные данные ребёнка — более строгий режим защиты (минимизация, отдельное согласие, ограничение передачи партнёрам по лояльности). ⚠ Конкретные требования законодательства РБ — проверить с юристом.
4. Запрет азартных игр/18+ категорий — реализуется технически через MCC-коды в `limits_engine`, независимо от итоговой юридической формулировки.
5. Банковская тайна vs доступ родителя к операциям подростка 14–17 — вероятная развилка; в продукте предусмотреть как настраиваемую (не финальную) политику. ⚠ Обсудить с юристом.
6. Итоговая оговорка для питча: «Правовые механизмы реализованы по общим принципам защиты несовершеннолетних и требуют финальной юридической проверки банка перед запуском в продакшн» — честная и ожидаемая формулировка, не слабость, а признак зрелости подхода.

### 1.5 Сценарий демо (`docs/demo-script.md`, 5 минут)
- 0:00–0:30 Проблема и концепция (слайд).
- 0:30–1:30 Путь родителя: онбординг в прототипе (выбор возраста → согласия → выпуск карты).
- 1:30–2:30 Путь родителя: AI-команда «поставь лимит 50 рублей в неделю на сладости» → превью → подтверждение (wow-момент).
- 2:30–3:30 Путь ребёнка: баланс, квест → баллы, AI-чат «сколько я потратил на игры?» — подчеркнуть «работает локально, офлайн, данные ребёнка никуда не уходят».
- 3:30–4:15 Путь подростка: запрос доступа к функции → родитель подтверждает → функция открывается.
- 4:15–4:45 Экономика (слайд, таблица окупаемости).
- 4:45–5:00 Закрытие + переход к Q&A (держать в запасе юр.оговорку и Canvas на технические вопросы).

## 2. Веб-прототип

### 2.1 Архитектура
```
Browser (React/Vite SPA) → REST (JWT) → FastAPI backend (mock core banking + AI gateway)
                                       │                    │
                                 SQLite/SQLAlchemy      Ollama localhost:11434
                                 (persistent DB)         (qwen2.5:1.5b/3b)
```
Запуск одной командой (`run.sh`/`Makefile`) на ноутбуке; Ollama — отдельный локальный сервис, модель должна быть заранее `ollama pull`-нута.

### 2.2 Backend (`backend/`)
```
backend/app/
  main.py, db.py (SQLAlchemy engine/session, SQLite файл для демо, легко переключить на Postgres)
  seed.py (1 демо-семья: родитель + ребёнок 10 лет + подросток 16 лет, 2–3 мес транзакций — создаётся отдельно от auth-флоу)
  models/ user.py card.py transaction.py limit.py goal.py quest.py loyalty.py access_request.py
  routers/ auth.py family.py cards.py transactions.py limits.py goals.py quests.py loyalty.py access_requests.py ai.py
  schemas/ (Pydantic, зеркало models/)
  services/ limits_engine.py rag.py ollama_client.py nl_command_parser.py
  core/ config.py (OLLAMA_URL, MODEL_NAME, DB_URL, JWT_SECRET, JWT_EXPIRE_MIN)
         security.py (хэширование паролей passlib/bcrypt, выпуск и проверка JWT)
         deps.py (get_current_user, get_current_parent — FastAPI Depends для защищённых роутов)
  tests/ test_auth.py test_limits.py test_access_requests.py test_ai_command_parser.py
```

**Авторизация и БД (обязательный слой, не демо-костыль):**
- Хранилище — SQLAlchemy + SQLite-файл (путь к БД в `.env`, легко заменить на Postgres без переписывания моделей). Таблицы: `users` (role: parent|child|teen, email, hashed_password, parent_id для детей), `families`, `cards`, `transactions`, `limits`, `goals`, `quests`, `loyalty_accounts`, `access_requests`. Данные переживают перезапуск backend — это и демонстрирует жюри, и упрощает повторные прогоны демо без пересоздания состояния.
- Регистрация: `POST /auth/register` — регистрируется родитель (email + пароль, bcrypt-хэш в БД). Профили детей не регистрируются самостоятельно — родитель создаёт их через `POST /family/onboarding`, при создании ребёнку присваивается собственный логин (например, email или короткий код) и временный пароль, который родитель передаёт ребёнку (повторяет реальный паттерн банковских детских приложений — ребёнок не проходит открытую саморегистрацию).
- Вход: `POST /auth/login` (email/логин + пароль) → JWT access-токен (с `role` и `user_id`/`family_id` в payload). Фронтенд получает токен через httpOnly cookie, выставляемый backend-ом при логине (безопаснее localStorage из-за XSS).
- Все остальные роуты — защищены `Depends(get_current_user)`; эндпоинты родителя (лимиты, approve/deny, выпуск карты) — дополнительно `Depends(get_current_parent)`, который проверяет, что ребёнок принадлежит семье текущего родителя (предотвращает доступ к чужим семьям).
- Пароли только в виде bcrypt-хэша, JWT-секрет из `.env` (не хардкод), срок жизни токена ограничен (напр. 60 мин) + `POST /auth/refresh` опционально.

Ключевые эндпоинты: `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `POST /family/onboarding`, `POST /cards/issue`, `POST /cards/{id}/block|unblock`, `GET /transactions`, `POST /transactions/simulate` (демо-кнопка покупки для показа лимита живьём), `GET/PUT /limits`, `GET/POST /goals`, `GET/POST /quests`, `POST /quests/{id}/complete`, `GET /loyalty/{user_id}`, `POST /access-requests`, `POST /access-requests/{id}/decide`, `POST /ai/chat`, `POST /ai/parent-command`.

AI-слой: `ollama_client.py` шлёт запрос на Ollama с системным промптом по роли. Для ребёнка — RAG через простой keyword/дата-фильтр по транзакциям (без векторной БД в MVP). Для родителя — `nl_command_parser.py` просит LLM вернуть JSON `{"action": "set_limit", "category": ..., "amount": ..., "period": ...}`, backend валидирует Pydantic-схемой; при сбое парсинга — явное «не понял, уточните». **Критично:** если Ollama недоступен — graceful fallback на rule-based ответ, чтобы демо не падало на сцене.

              limits/LimitEditor.tsx goals/GoalProgress.tsx quests/QuestBoard.tsx loyalty/PointsWidget.tsx
              access/AccessRequestList.tsx ai/ChatWidget.tsx auth/ProtectedRoute.tsx (редирект на /login без токена)
  pages/
    Auth/ LoginPage.tsx RegisterPage.tsx (регистрация родителя)
    Onboarding/ ChooseAgeStep.tsx ConsentStep.tsx IssueCardStep.tsx (создание профиля ребёнка/подростка с его логином)

    ChildDashboard/ Home.tsx GoalsPage.tsx QuestsPage.tsx RequestAccessPage.tsx AiChatPage.tsx

Настоящая авторизация: `LoginPage` (логин/email + пароль) → `POST /auth/login` → JWT сохраняется (httpOnly cookie, выставляемый backend-ом при логине) → `ProtectedRoute` проверяет сессию через `GET /auth/me` при загрузке приложения и редиректит неавторизованных на `/login`. Для демо — родитель логинится один раз, подросток/ребёнок логинятся под своими учётными данными (можно открыть второй профиль браузера/вкладку в приватном режиме, чтобы показать обе роли одновременно на сцене). Брендинг (цвета/логотип) взять из `TZ/Family banking_Hackaton.pdf` (синяя палитра МТБанк/Moby), чтобы UI не выглядел как типовой bootstrap-шаблон.

## 3. Roadmap (без жёстких дедлайнов, этапы — логическая последовательность)

0. **Фундамент** — создать структуру папок `backend/`, `frontend/`, `ai/`, `docs/`, базовый `README.md`.
1. **Backend skeleton + авторизация + БД** — FastAPI, SQLAlchemy-модели, `auth.py` (register/login/me, bcrypt, JWT), `deps.py` (get_current_user/get_current_parent), CRUD-роуты без AI, seed-скрипт отдельно от auth-флоу. Критерий: можно зарегистрировать родителя, залогиниться, получить JWT, через него создать семью/ребёнка и дойти до защищённых эндпоинтов; неавторизованный запрос к защищённому роуту — 401; `pytest` зелёный (включая `test_auth.py`); `/docs` Swagger работает.
2. **Frontend skeleton + реальный логин** — `LoginPage`/`RegisterPage`, `AuthContext`, `ProtectedRoute`, Onboarding, ParentDashboard/Overview, ChildDashboard/Home. Критерий: happy path вручную без AI, но с настоящим логином — регистрация родителя → онбординг ребёнка (ребёнок получает логин/пароль) → выход → вход как ребёнок → выпуск карты виден → лимит → демо-покупка → блокировка по лимиту. Перезапуск backend не теряет данные (БД персистентна).
3. **Геймификация и лояльность** — квесты, цели, баллы. Критерий: ребёнок выполняет квест → получает баллы → родитель видит прогресс.
4. **Access requests** — запрос прав ребёнком → approve/deny родителем → реальное применение права.
5. **AI-слой (Ollama)** — `/ai/chat` (RAG), `/ai/parent-command` (NL→команда+превью+подтверждение), fallback без Ollama. Критерий: оба AI-сценария демо работают на реальных seed-данных.

## 5. Решения перед стартом кодинга
1. Хранилище — SQLite через SQLAlchemy (не in-memory dict) ради устойчивости демо и реальной персистентности между перезапусками; миграции — `SQLAlchemy.metadata.create_all` при старте приложения достаточно для хакатона, Alembic — избыточен.
2. Авторизация — пароли только bcrypt-хэшем, токен JWT с ограниченным сроком жизни, передаётся через httpOnly cookie (не localStorage) для защиты от XSS; `JWT_SECRET` берётся из `.env`, не хардкодится в коде.
3. Модель Ollama — протестировать `qwen2.5:1.5b` vs `qwen2.5:3b` на железе разработчика по скорости/стабильности JSON-вывода; держать rule-based regex-парсер как подстраховку для простых команд лимита.
4. Брендинг — извлечь синюю палитру/логотип Moby из `TZ/Family banking_Hackaton.pdf`.
